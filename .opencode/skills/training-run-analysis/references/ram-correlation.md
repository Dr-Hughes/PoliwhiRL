# RAM correlation reference

## Evidence hierarchy

Use evidence in this order:

1. Verified event-flag and map tables in `RAM_MAPPING.md`.
2. Runtime checkpoint definitions in `PoliwhiRL/checkpoints.py`.
3. Per-episode fire steps and seeded provenance in the checkpoint/metrics data.
4. First-hit replay manifests and PNGs as deterministic debugging evidence.

Never infer a story checkpoint solely from reward magnitude. Several reward
channels can fire on the same step, and depletion changes their value over time.

## Data joins

The checkpoint-aligned arrays in `info.pth` live under `episode_data`:

| Field | Use |
|---|---|
| `episode_flag_fire_steps[i]` | Derived checkpoint flags and their steps in episode `i` |
| `episode_seeded[i]` | Whether episode `i` began from a Go-Explore snapshot |
| `episode_reward_sources[i]` | Per-source reward totals for episode `i` |
| `episode_unique_maps[i]` | Episode-local map coverage |
| `episode_unique_cells[i]` | Episode-local unique-cell coverage |
| `episode_archive_size[i]` | Run-wide archive size after episode `i` |
| `discovery_log` | Parent-deduplicated run-wide first discoveries |
| `probe_goal_rates` | Labelled true-start short-probe rates |
| `long_probe_goal_rates` | Labelled true-start long-probe rates |

Top-level `checkpoint_recordings` is keyed by flag number and records the first
honest live hit plus its replay result. Top-level `visit_archive` records run-wide
cell, map and milestone counts. Top-level `frontier_pool` records persisted
Go-Explore seed states.

The JSON metrics use shorter names such as `flag_fire_steps`, `seeded`,
`reward_sources`, `unique_maps`, `unique_cells` and `archive_size`.

## Interpreting a route

A route is a conjunction of evidence, not one number. For the Mystery Egg chain:

1. `(26, 10)` in map coverage proves the house was entered.
2. Flag `30` proves the Egg interaction completed.
3. Flag `31` proves the Egg was returned to Elm.
4. `episode_seeded == false` on the flag-31 episode proves an honest complete
   route from the canonical start.
5. Repeated flag-31 true-start probe success establishes reliability.

If only seeded flag-31 episodes exist, say that the downstream checkpoint is
reachable from supplied frontier states but that end-to-end competence remains
unproven.

## Fire-step sanity checks

- Flag steps are one-based environment steps.
- Multiple flags can fire in one episode; preserve each pair.
- A map visit can precede its interaction flag by only a few steps.
- Episode horizon comparisons should use the deepest relevant fire step, not the
  mean of all early flags.
- Checkpoint reward depletion is indexed by persistent fire count, so later
  successful episodes can receive a smaller direct reward despite equivalent
  progress.

## Recording sanity checks

The first-hit recorder deliberately captures only honest episodes and durable
flags. Its action trace begins after the environment's reset/baseline step and
ends with the action that caused the one-based checkpoint fire step. The replay
must observe the same flag before its status becomes `recorded`.

Folder names are generated by `checkpoint_slug(flag)` and are stable and
sortable. Treat metadata titles as display text; use the numeric flag as the
join key.
